# Stage 2 findings — unified schema, campaign labeling, leak-free split

## What's implemented

`scripts/stage2_parse_darpa2000.py` and `scripts/stage2_parse_cicids2017.py`
turn each raw source into the shared unified event schema (`src/schema.py`:
timestamp, src/dst IP and port, service, tier, campaign_id, kill_chain_stage,
attack_type, is_campaign_link), and derive campaign-membership ground truth
and a leak-free train/test split. `src/leakage.py`'s
`assert_no_campaign_leakage` and `assert_dataset_is_test_only` are the
concrete, checked-in-code guarantees behind every "no campaign straddles the
split" and "DARPA never touches training" claim made in later stages.

## DARPA2000: two real bugs caught while deriving campaign membership

Campaign membership was derived from the data itself, not assumed: an
internal IP is a "campaign host" if it appears in phase 4 (install) records
-- i.e. actually reached compromise, not just probed. Two mistakes surfaced
and were fixed before this was trustworthy:

**Bug 1 -- spoofed flood sources polluting the host set.** The first
attempt derived campaign hosts from phases 4 *and* 5 combined. Phase 5 is
the DDoS launch, which uses spoofed source IPs by design, so this pulled in
thousands of one-off forged addresses as if they were real campaign
members. Fixed by deriving hosts from phase 4 only, and using the flood's
stable *destination* (not its spoofed sources) when phase 5 needed to
contribute anything.

**Bug 2 -- the attacker's own IP making the membership check nearly
vacuous.** Even after fixing Bug 1, LLDOS 1.0 showed zero distractor
events -- every recon probe counted as "in campaign." Cause: the check
allowed a match on *either* side of a packet, and the attacker's external
IP (202.77.162.213) is trivially present on every probe packet, including
ones against hosts that were never compromised. Fixed by restricting the
host-matching set to the internal 172.16.0.0/16 address space, so
membership is decided by whether the *target* actually got compromised, not
whether the attacker was merely involved.

**Result after both fixes:** LLDOS 1.0 gives a genuine, non-degenerate
split -- 150 true campaign-linked events vs. 134 same-time-window
distractor events (dead-end probes against hosts that never escalated).
LLDOS 2.0.2 (the "stealthy" variant) has zero within-scenario distractors
-- checked directly against the raw data and confirmed to be a real,
documented property of that scenario's design (it probes only the host it
goes on to compromise), not a parsing artifact. Practical consequence,
carried into Stage 5: LLDOS 2.0.2 can't supply its own negatives, so the
external evaluation must pool it with LLDOS 1.0 for the correlator to have
real distractors to reject.

The DDoS flood itself (~67,000 near-duplicate spoofed packets across both
phase-5 captures) was collapsed into 1-second aggregate events via
`src/aggregate.py` -- a real SOC doesn't receive 33,000 individual alerts
for one flood, and leaving them as individual rows would have let sheer
repetition dominate every downstream count. Final output: 316 unified
DARPA2000 events, explicitly marked test-only.

## CICIDS2017: no native campaign labels, and shared-IP grouping doesn't work

CICIDS2017 ships no multi-stage campaign labels at all -- every attack type
is a separate single-technique capture. Worse, the signal that worked for
DARPA (shared IP) is useless here: **every attack type, without exception,
was generated by the same fixed attacker VM (172.16.0.1) against the same
fixed victim (192.168.10.50)**. Campaigns were instead derived via
time-gap clustering: attack-type blocks within 60 minutes of each other on
the same day are merged into one campaign. Cross-checked against the
officially published CIC-IDS2017 attack schedule (Sharafaldin et al. 2018 --
Tue=brute force, Wed=DoS, Thu=web attacks, Fri=botnet/scan/DDoS) for face
validity, this produced 6 campaigns matching that schedule exactly:

- `cicids2017_tue_c0` (FTP-Patator), `cicids2017_tue_c1` (SSH-Patator) -- kept separate, >1hr apart
- `cicids2017_wed_c0` (Slowloris, Slowhttptest, Hulk, GoldenEye -- merged, contiguous)
- `cicids2017_wed_c1` (Heartbleed -- separate, hours later)
- `cicids2017_thu_c0` (Brute Force, XSS, SQL Injection -- merged, CIC's documented "web attacks" block)
- `cicids2017_fri_c0` (Botnet, Port Scan, DDoS -- merged, overlapping)

This is a **derived** grouping, not native ground truth like DARPA's phase
structure -- stated explicitly here and repeated in Stage 6, not glossed
over. Split 4 campaigns train / 2 val, leak-free split verified in code
(`assert_no_campaign_leakage`). Benign distractor rows sampled at 5x each
day's attack-row count (capped 50k/day, fixed seed) as the negative pool.
Same flood-aggregation policy as DARPA applied to every attack type
exceeding 200 raw rows. Final output: 58,057 unified events (13,720 true
campaign-linked, 44,337 distractor).

**Scope note carried forward to Stage 6:** `tier` is set to `"network"` for
every CICIDS2017 event, including `web_sql_injection`/`web_xss`. These are
still network-flow-level captures (5-tuple + flow statistics) -- there is
no HTTP method/URL/payload field in this schema, so they are not genuine
web/WAF-tier alerts. That gap was never closed (the DVWA + ModSecurity
source was deferred at Stage 1 and never built).

**Stage 4 addendum, added later:** each CICIDS2017 event also carries a
`predicted_attack_type`/`predicted_kill_chain_stage`, scored by Stage 3's
trained classifier at parse time (not ground truth) -- this is what lets
Stage 4's DQN train against the identifier's *actual* predictions,
including its real errors, rather than an idealized oracle label. Doing
this at full column width for every raw CICIDS2017 file, one file at a
time, immediately trimmed back down before the next file loads, is what
keeps this memory-safe on the 2-core/4GB box this project ran on -- see
`scripts/stage2_parse_cicids2017.py`'s module docstring for the exact
mechanism.

## Why this matters for everything downstream

Every leak-free-split claim in Stages 3-5 traces back to the checks built
here. DARPA2000's reservation as test-only data is enforced, not just
promised: `assert_dataset_is_test_only` runs at the start of Stage 4
training and would raise immediately if any `darpa2000_*` row ever appeared
in a training dataframe. The campaign-derivation bugs caught in this stage
are also the clearest illustration in the whole project of the "investigate
before treating as good" discipline applied *before* any model was ever
trained -- getting the ground truth right came first.
